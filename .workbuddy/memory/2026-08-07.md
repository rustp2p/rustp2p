## 修复 rustp2p-quic 单向 bootstrap 路由确认缺陷

**问题**: UDP 传输下单向 bootstrap 时，接收方（被连接方）从不确认发起方的直连路由，导致三个 bug：
1. 接收方 send 报 "route not found"
2. peers 显示 direct=false
3. stream 数据接收不到

**根因**: `protocol.rs` HelloRequest 处理器调用 `confirm_tcp_route`，该函数对 UDP 是空操作（仅确认 TCP 路由）。只有发起方在收到 HelloReply 时调用 `confirm_peer_route` 确认路由。

**修复**:
1. `protocol.rs:654` — HelloRequest 处理器: `metric==0` 时改用 `confirm_direct_and_promote` 确认 UDP 直连路由（根因修复，解决全部三个 bug）
2. `quic.rs:612` — `handle_incoming_stream` 将 `ensure_peer_reachable` 替换为 `route_metric_for`，与 `handle_incoming_datagram` 一致（入站流纵深防御）
3. `protocol.rs:1056` — 新增 `confirm_direct_and_promote` 辅助方法：确认路由后自动从 `route_candidates` 移除候选条目，防止冗余探测和内存泄漏
4. `protocol.rs:1106` — 维护循环中新增主动候选路由探测：遍历 `route_candidates`，对未确认的候选发送 HelloRequest，利用现有 HelloReply 处理器完成双向确认。这与打洞逻辑无关——HelloRequest/HelloReply 是传输无关的双向可达性验证
5. `tests/high_level.rs` — 新增 `one_way_bootstrap_both_directions_can_send` 和 `one_way_bootstrap_stream_works` 测试

**安全性验证**:
- 修复1仅由 HelloRequest 触发，与 PunchRequest/PunchReply 完全独立
- metric==0 证明数据包直连到达，NAT打洞必须已成功才能收到
- `confirm_direct_and_promote` 与 PunchReply 确认调用同一底层函数，行为一致
- `upsert_peer_info` 的 `is_direct |= existing` 只升不降，不会覆盖已有直连属性
- `add_route_` 新增直连路由时清除同 peer 的中转路由（与 PunchReply 行为相同，非修复1引入）

**设计考量**: `route_candidates` 是两层路由模型中的"半验证"层——仅证明对端→我们，未证明我们→对端。原设计 `ensure_peer_reachable` 有意不回退候选，用于 `connection_to`（出站连接门控）。修改 2 原方案全局回退候选会改变出站连接语义，后改为只在 `handle_incoming_stream` 用 `route_metric_for`，保持 `ensure_peer_reachable` 原始语义不变。主动探测是用户提出的方案——不关心直连还是中转，只验证"我发了→对方回了→双向通"。

**验证**: 30 tests passed (rustp2p-quic: 20 unit + 9 integration + 1 doc), 15 tests passed (rustp2p-core), node example 编译通过

## 打洞路由确认逻辑深度分析

**发现额外 bug**: 打洞的 PunchReply 永远无法匹配 `pending_punch`，直连路由无法通过打洞机制确认：
- `punch()` 记录 `pending_punch[request_id_1]`，发 PunchRequest via relay (id_1)
- `execute_punch()` 用 `rand::random()` 生成新 request_id_2，直接发送 PunchRequest，**不记入 pending_punch**
- PunchRequest 接收方回复 PunchReply 时 echo 同一个 request_id
- relay PunchReply (id_1, metric>0) → 匹配 pending_punch 但 metric>0 不确认
- direct PunchReply (id_2, metric==0) → **不匹配** pending_punch (只有 id_1) → 不确认!
- 接收方 B 从未调用 `punch()`，B 的 pending_punch 为空 → B 侧也永远不确认

**实际确认路径**: 打洞创建 `route_candidates` 条目 → 维护循环探测发送 HelloRequest → HelloReply 回来后确认。打洞机制本身不确认路由，只负责 NAT 穿透和创建候选。

**路由共存**: 默认 `LoadBalance::MinHopLowestLatency` 下，`add_route_` 确认直连路由时执行 `list.retain(|k| k.is_direct())`，清除所有中转路由。直连和中转**不共存**。风险：NAT 映射过期后中转路由已清除，通信中断需重新 bootstrap。

## 修复打洞 request_id 匹配 bug + 路由共存

**修复6**: `protocol.rs:840` — `execute_punch` 在发送 PunchRequest 前将 `request_id` 记入 `pending_punch`，使直接 PunchReply 能匹配并确认直连路由。之前 `execute_punch` 生成新 `request_id` 但不记录，导致 PunchReply 永远不匹配。

**修复7**: `route_table/table.rs:371` — `add_route_` 三处改动实现路由共存：
1. metric 检查仅在同类型路由间生效（`x.is_direct() == route.is_direct()`），允许直连和中转共存
2. 移除 `list.retain(|(k, _)| k.is_direct())` 清除中转路由的逻辑
3. 排序改为 `sort_key()`（metric, rtt），直连路由优先；先 push 再排序确保新路由参与排序
4. 防止直连路由被降级：同 route_key 的直连路由不更新为 metric>0（IDRouteQuery 响应通过同一路径返回但携带更高 metric）

**修复8**: `tests/high_level.rs` — 新增 `direct_and_relay_routes_coexist` 测试验证三节点链路中直连和中转路由共存

## 打洞自动化修复 + punch_whitelist 改为 Option + 日志完善

**问题**: 用户三节点测试（两NAT后+一公共服务器），RUST_LOG=debug 完全看不到打洞信息。

**根因分析（4个阻断点）**:
1. `punch()` 是纯手动API，维护循环从不调用 → 打洞永远不触发
2. `punch_whitelist` 默认空Vec → `punch_allowed()` 永远返回false
3. `max_assistant_sockets` 默认0 → Symmetric NAT 检测后不创建辅助UDP
4. 打洞代码路径无任何 debug/info 日志

**修复**:
1. **punch_whitelist 改为 `Option<Vec<PeerId>>`**：`None`=全部允许（默认），`Some(vec)`=显式白名单
   - `protocol.rs`: 字段改为 `RwLock<Option<HashSet<PeerId>>>`，`punch_allowed` 在 None 时返回 true
   - `config.rs`: `punch_whitelist: Option<Vec<PeerId>>`，默认 None
   - `endpoint.rs`: builder 和 API 方法签名更新
   - `deny_punch` 在 None 时切换为 `Some(HashSet::new())`（显式空集）
2. **维护循环自动打洞**：每1秒检查已知peer，对满足条件的peer自动触发 punch
   - 条件：punch_allowed + 无直连路由 + 有peer_nat信息 + 10秒速率限制
   - 先 best-effort 通过 relay 发 PunchRequest 通知对端回打
   - 再直接 execute_punch 发送 UDP/TCP 打洞包
   - 新增 `last_punch_time: DashMap<PeerId, u64>` 速率限制
3. **打洞日志**：
   - `protocol.rs`: PunchRequest/PunchReply 处理添加 debug 日志，打洞成功添加 info 日志
   - `protocol.rs`: execute_punch 添加 debug 日志显示目标、NAT类型、映射地址
   - `protocol.rs`: NAT 检测结果添加 info 日志
   - `punch/mod.rs`: punch_now、punch_udp 添加 debug 日志
   - 维护循环 auto-punch 添加 debug 日志
4. **node 示例**：添加 `--max-assistant-sockets <n>` 参数和 `punch <peer_id>` 命令
5. **测试**：`node()` helper 设置 `set_punch_whitelist(Some(vec![]))` 禁用自动打洞，避免本地测试拓扑被干扰

## 修复 STUN 检测结果未填充公网 IP/端口（打洞目标地址错误根因）

**问题**: 用户三节点测试，打洞目标地址与 STUN 检测到的映射地址不匹配：
- node-c STUN 检测到 `222.186.160.18:59160`，但 node-b 打洞目标为 `222.186.160.18:6000`（本地绑定端口）
- node-b STUN 检测到 `223.68.65.170:2735/2776`，但 node-c 打洞目标为 `223.68.65.170:2779`（本地绑定端口）
- 双方都看不到对方打洞过来的包

**根因**: `apply_stun_result_to_nat_info` 只复制 `nat_type` 和 `port_range`，**丢弃了** `StunResult` 中的 `public_ipv4`、`public_udp_ports`、`public_ipv6`。

**链路分析**:
1. STUN 正确检测到公网 IP 和映射端口
2. `apply_stun_result_to_nat_info` 丢弃公网信息 → `NatInfo.public_ips` 和 `public_udp_ports` 保持为空
3. NatInfo 通过 HelloReply/PunchRequest 交换给对端 → 对端收到的 NatInfo 缺失公网地址
4. `flag()` 优先级：`public_ipv4_addr()`（空）→ `public_ipv4_tcp()`（空）→ `local_ipv4_addrs()`（返回本地绑定地址）
5. 打洞目标变成 `本地IP:本地绑定端口` 而非 `公网IP:STUN映射端口`
6. 包发到错误地址 → 对端永远收不到

**修复**:
- `protocol.rs` `apply_stun_result_to_nat_info`: 新增复制 `public_ipv4` → `public_ips`、`public_udp_ports`、`public_ipv6` → `ipv6`
- `protocol.rs` 测试: `stun_update_does_not_fill_public_ports_or_ipv6` → `stun_update_fills_public_ports_and_ipv6`，断言公网信息被正确填充

**验证**: 46 tests passed, node example 编译通过

## 回退 STUN 公网地址填充 + 修复 Symmetric NAT 端口预测 + NatObserve 日志

**问题**: 之前的修复（从 STUN 复制 public_ips/public_udp_ports）是错误的，因为 STUN 用的是临时 socket（bind 0.0.0.0:0），探测到的端口不是主 QUIC socket 的映射端口。正确的做法是通过 NatObserve（直连服务器观察）获取公网地址。另外 Symmetric NAT 端口预测完全失效——从全局随机数组过滤小范围，命中率≈0.076/60。

**根因分析**:
1. STUN `stun_test_nat0` 绑定 `0.0.0.0:0`（随机端口），探测到的映射端口是临时 socket 的，不是主 QUIC socket 的
2. 原始设计意图（DESIGN.md）：STUN 只负责 NAT 类型 + port_range，公网 IP/端口由 NatObserve 提供
3. 端口预测 bug：从 shuffled_ports（1-65535）取60个随机端口，过滤在预测范围内的（如 [2694,2776]），命中期望≈0.076，几乎从不执行
4. 旧版本（0.4.0）正确做法：在范围内生成所有端口，shuffle 后取前 k 个

**修复**:
1. **回退 `apply_stun_result_to_nat_info`**: 恢复为只复制 nat_type 和 port_range，不复制 public_ips/public_udp_ports/public_ipv6
2. **auto-punch 增加公网地址检查**: 跳过 public_ips 或 public_udp_ports 为空的 peer（NatObserve 未完成）
3. **NatObserve 日志**: 请求发送、回复接收、observation 应用均添加 debug/info 日志
4. **端口预测修复** (`punch/mod.rs`):
   - Phase 1: 在 `[port - range, port + range]` 范围内生成所有端口，shuffle 后取前 max_k1 个
   - 遍历所有已知端口（不只第一个）作为预测基准
   - 发送到所有公网 IP（不只第一个）
   - Phase 2（全局随机扫描）保持不变
5. **Cone NAT 修复**: 发送到 `public_ipv4_addr()` 返回的所有地址，不只第一个
6. **测试**: `stun_update_fills_public_ports_and_ipv6` → `stun_only_updates_nat_type_and_port_range`

## 修复 STUN port_range=0 + public_udp_ports fill(0)（Symmetric NAT 端口预测根因）

**问题**: 用户日志显示 `NAT type detected: Symmetric (port_range=0)`，端口预测完全失效。

**根因分析（两个独立 bug）**:

1. **stun_test_nat/stun_test_nat_with_socket break 跳过赋值**（stun/mod.rs）:
   - 内层函数 `stun_test_nat0` 正确计算了 `port_range = max_port - min_port`
   - 但外层函数检测到 Symmetric 后 `nat_type = Symmetric; break;`，跳过了 port_range 提取
   - port_range 始终保持初始值 0

2. **public_udp_ports fill(0)**（endpoint/service.rs）:
   - `nat_info()` 将 `public_udp_ports` 设为 `local_udp_ports.clone()` 然后 `fill(0)`
   - 产生 `[0, 0, ...]`，在 punch Symmetric 分支中 base_port=0 生成空范围 (1..=0)
   - STUN 用临时 socket，端口不可用；真实端口应由 NatObserve 提供

**修复**:
1. stun_test_nat / stun_test_nat_with_socket: 在 break 前提取 port_range、public_ipv4、public_udp_ports、public_ipv6
2. endpoint/service.rs: `public_udp_ports` 改为空 Vec，由 NatObserve 填充真实端口

**修复后数据流**: STUN(port_range=43) → NatInfo(public_udp_ports=[], port_range=43) → NatObserve(public_udp_ports=[observed_port]) → 对端收到 → Phase1 预测 [observed_port-43, observed_port+43] = 87个端口
